# Memory model

> **Status:** accepted · **Checkpoint:** 0 (design) · 3 (working)

## 1. Principles

1. **Everything is static.** No heap in the kernel
   ([ADR-0003](../adr/0003-no-kernel-heap.md)). Total RAM is known at link time;
   running out is a build error, not a field failure.
2. **Every region has exactly one owner.** No implicit sharing between
   protection domains.
3. **The layout is a reviewed artefact.** `layout.md` is generated and
   committed, so a pull request that grows a stack by 4 KiB shows up as a diff
   somebody sees.
4. **Isolation is opt-out**, never opt-in.

## 2. Address-space layout

On the Nucleo-F767ZI (STM32F767ZI: 2 MB flash, 512 KB RAM):

```text
FLASH  0x0800_0000 ┌────────────────────────┐
                   │ vectors                │  kernel, RX
                   │ kernel .text           │  kernel, RX
                   │ task .text             │  per task, RX
                   │ .rodata                │  RO
                   │ manifest metadata      │  RO — build id, task table, layout
       0x0820_0000 └────────────────────────┘

DTCM   0x2000_0000 ┌────────────────────────┐  128 KB, zero wait state
                   │ kernel .data / .bss    │  kernel, RW
                   │ kernel stack           │  kernel, RW
                   │ hot task stacks        │  per task, RW
                   └────────────────────────┘

SRAM1  0x2002_0000 ┌────────────────────────┐  368 KB
                   │ task stacks + guards   │  per task, RW
                   │ task .data / .bss      │  per task, RW
                   │ channel storage        │  endpoints only, RW
                   │ DMA buffers            │  owning task, RW
                   │ crash dump buffer      │  kernel, RW
                   └────────────────────────┘

                   ┌────────────────────────┐
                   │ peripherals            │  by capability, MMIO
                   └────────────────────────┘
```

**DTCM matters on the M7.** Tightly-coupled memory has no cache and no wait
states, so access time is deterministic. Placing the hard real-time tasks'
stacks there removes cache behaviour from their timing — which is the single
most useful thing you can do for WCET credibility on this part. The manifest
will gain a placement hint for this in Checkpoint 3; until then it is a
board-level decision.

## 3. Task memory

Each isolated task owns:

| Region | Permissions | Notes |
|---|---|---|
| Code | RX | Shared read-only text is permitted |
| Stack | RW | Preceded by a guard region |
| Static data | RW | `.data` and `.bss` |
| Channel storage | RW | Only channels it is an endpoint of |
| Peripherals | MMIO | Only those it declared |

### Stack guards

A guard region sits **below** every stack (stacks grow down). It is programmed
with no access, so the first overflowing access faults — before adjacent memory
is touched.

This is `ARCH-FAULT-002` and is required for any port claiming tier 1 or above.
The common alternative — a canary checked at context-switch time — detects the
overflow *after* the damage, at an unknown remove from the cause. That is enough
to know something went wrong and not enough to know what.

### The ARMv7-M alignment cost

ARMv7-M protection regions must be **powers of two and naturally aligned**:

```text
declared 3KiB  →  region 4KiB  →  1024 bytes wasted
declared 2KiB  →  region 2KiB  →  no waste
declared 5KiB  →  region 8KiB  →  3072 bytes wasted
```

The validator reports this per task (M0012) with the exact byte cost and
suggests rounding up so the cost becomes an explicit decision. On ARMv8-M
(32-byte granularity) the waste largely disappears — one of the concrete reasons
that architecture is the strategic target
([ADR-0001](../adr/0001-target-architecture.md)).

### Region budget

ARMv7-M provides 8 regions. A typical isolated task spends them roughly:

```text
1  kernel text (shared, RX)
2  task text (RX)
3  task stack (RW)
4  task .data/.bss (RW)
5  stack guard (no access)
6  channel storage (RW)
7  peripheral A (MMIO)
8  peripheral B (MMIO)
```

**That is the whole budget.** A task needing three peripherals and two channels
does not fit. This is the design's sharpest practical constraint, and the
build-time allocator must produce an error naming the task, listing what it
asked for, and suggesting what to merge — not a runtime failure.

The allocator applies two reductions before giving up: adjacent regions with
identical permissions are merged, and peripherals in a contiguous address range
can share one region at the cost of coarser granularity — which is a real
security trade and is therefore reported, not applied silently.

## 5. DMA

DMA is the reason type safety alone is not enough. A DMA engine writes to
whatever address its descriptor holds, and consults nothing.

Malleus's rules:

1. **DMA buffers are owned by a task** and live inside that task's regions.
2. **Descriptors are validated** against the owning task's regions before the
   transfer is armed.
3. **A transfer cannot target memory outside the task** — `ARCH-MPU-003`, tested
   on hardware, not in simulation.
4. **Cache maintenance is explicit.** On the Cortex-M7, forgetting to clean or
   invalidate around a DMA transfer produces corruption that appears only at
   speed and only sometimes. The DMA API makes the operation mandatory rather
   than a documented obligation.

## 6. What this model does not do

- **No virtual memory.** No MMU on these parts, and none is wanted.
- **No demand paging, no swap.**
- **No memory compaction** — nothing moves.
- **No zero-copy between isolated tasks.** A hardware boundary means either a
  copy or an explicitly declared shared region. There is no way around this.
- **No protection against a physical attacker** — see
  [threat model](01-threat-model.md).
