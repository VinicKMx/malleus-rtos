# ADR-0010 — Every `unsafe` block is documented, justified, and inventoried

> **Status:** Accepted · **Checkpoint:** 0

## Context

A kernel cannot be written in safe Rust. Context switching manipulates the stack
pointer. Memory protection writes to registers that change the meaning of every
subsequent access. Interrupt handling runs outside the model the borrow checker
assumes. All of this is `unsafe`, necessarily.

That makes "Malleus is written in Rust" a weaker claim than it sounds, and the
project would be dishonest to lean on it without saying where the guarantees
stop. The interesting question is not whether there is `unsafe` code — there is —
but whether each use is **necessary, minimal, justified, and reviewed**.

There is a second motivation. Any future path toward safety certification —
IEC 61508, ISO 26262, IEC 62304 — requires evidence produced *during*
development. Evidence reconstructed afterwards is worth much less and costs far
more. Qualified toolchains such as Ferrocene make such a path plausible for
Rust, but a qualified compiler certifies the compiler, not your kernel: the
project must produce its own evidence and respect the qualification's scope.
None of that is a Checkpoint 0 concern — but *starting* the habit is, because
this is the one thing that cannot be retrofitted.

## Decision

**Every `unsafe` block carries a `SAFETY:` comment stating the invariants that
make it sound. This is machine-enforced.**

```toml
[workspace.lints.clippy]
undocumented_unsafe_blocks = "deny"
missing_safety_doc = "deny"
```

```rust
#![forbid(unsafe_op_in_unsafe_fn)]  // every no_std crate
```

`unsafe_op_in_unsafe_fn` is forbidden, not merely denied: an `unsafe fn` does
not implicitly make its body an `unsafe` block, so each operation inside must
still be justified individually. Without it, a large `unsafe fn` becomes a place
where unsafety hides in plain sight.

### Additional rules

1. **`unsafe` is confined to `malleusrt` and `malleus-arch-*`.** Host tooling has
   none. Application code has none unless the application chooses it.
2. **Every `unsafe fn` and `unsafe trait` has a `# Safety` section** stating the
   caller's obligations — enforced by `missing_safety_doc`.
3. **Minimal scope.** `unsafe { a(); b(); }` where only `a` needs it is a review
   comment, every time.
4. **A named invariant.** Kernel invariants get stable identifiers
   (`FaultKind::KernelInvariant { invariant: &'static str }`) cross-referenced in
   `docs/internals/invariants.md`, so a violated invariant in a crash dump is
   traceable to its documentation.
5. **Two reviewers** for any change touching `unsafe` in the kernel or an arch
   crate.
6. **An inventory artefact** — every block, its file, its invariants, and its
   test coverage — generated by `cargo xtask unsafe` and published with each
   release, starting at Checkpoint 1.

### The related lint decision

`arithmetic_side_effects` and `indexing_slicing` are denied in `malleusrt` and
`malleus-arch` — a panicking add inside a scheduler is a system that stops
scheduling — and deliberately **not** applied to host tooling, where the same
rules buy nothing and cost readability.

Applying a rule where it does not pay is how a codebase learns to reach for
`#[allow]` by reflex, and a codebase that reaches for `#[allow]` by reflex will
do it in the kernel too.

## Consequences

### What this buys

- The `unsafe` surface is bounded, visible, and countable.
- Review effort concentrates where it matters.
- Safety evidence accumulates from day one instead of being reconstructed.
- A crash dump naming a violated invariant points at its documentation.
- The claim "written in Rust" is backed by something checkable.

### What this costs

- **Writing `SAFETY:` comments is real work,** and a rushed one is worse than
  none because it looks like review happened.
- **Two-reviewer policy slows kernel changes**, which is felt most in a
  single-maintainer project — where it is also least effective, and this should
  be acknowledged rather than pretended away.
- **The inventory is maintenance** that never ends.
- **Lint discipline occasionally forces awkward code.** `checked_div` where `/`
  would read better. That is the intended trade in the kernel and the reason the
  lints stop at its boundary.

### What it forecloses

Nothing technical. It makes some changes slower, which is the point.

## Alternatives considered

**`#![forbid(unsafe_code)]` everywhere.** Impossible for a kernel. Some projects
achieve it by pushing `unsafe` into a dependency, which relocates the problem
and obscures it.

**Documentation by convention, no lint.** Rejected: conventions decay, and the
decay is invisible until someone audits. A denied lint fails the build the day
the convention is broken.

**Formal verification of `unsafe` blocks** (Kani, Prusti, MIRAI). Genuinely
attractive and worth revisiting. Rejected for now as too much machinery before
there is a kernel to verify — but it is the natural next step once one exists,
and the invariant identifiers are chosen partly to make it possible.

**Defer safety evidence until certification is actually pursued.** Rejected:
this is the one thing that cannot be retrofitted. Reconstructing rationale for
code written three years ago, by someone who may have left, is the most
expensive form of this work.

## Revisit when

- Checkpoint 1 delivers a kernel and the inventory becomes real rather than
  aspirational. The policy should be re-examined against what it actually cost.
- Formal verification tooling for `unsafe` Rust matures enough to apply to a
  kernel of this size.
- A certification path is genuinely pursued, at which point the evidence
  requirements become specific and this ADR is superseded by something far more
  detailed.
